# 2. DNS по сервисам: ChatGPT, Claude

Некоторые сервисы блокируют не провайдеры, а **сами сервисы** не пускают пользователей из России. Обходится это
DNS-прокси: специальный DNS-сервер на запрос `chatgpt.com` отдаёт адрес своего прокси за границей, и трафик идёт
через него.

Такие DNS-сервисы есть (GeoHide, Bezmezhau, Comss и другие). Они появляются, меняют адреса и закрываются, поэтому
**актуальные адреса и имена (для DoT) берите на их сайтах**.

## 2.1. Почему DoT и почему «по доменам»

- Обычный DNS (UDP 53) провайдер видит и может подменить. **DoT (DNS-over-TLS)** шифрован.
- Если поставить один DoT-сервер **на всё**, то когда он упадёт (а бесплатные падают), пропадёт DNS у всего дома.
- В Keenetic у DoT-сервера есть поле **«Домен»**: сервер используется **только для этого домена и его поддоменов**.
  Остальное идёт через обычный DNS провайдера. Это и надо.

## 2.2. Настройка

**Сетевые правила → Интернет-фильтры → Настройка DNS** (в разных версиях: «Интернет-безопасность → DNS»)
→ **Добавить сервер**:

| Поле | Что вписать |
|---|---|
| Тип | DNS-over-TLS |
| Адрес | IP DoT-сервера сервиса, например `<IP_DNS_СЕРВИСА>` |
| Имя (SNI) | имя сервера, например `<dns.сервис.ru>` |
| Домен | `chatgpt.com` |

Повторите для каждого домена (один сервер, разные домены):
- ChatGPT: `chatgpt.com`, `openai.com`, `oaistatic.com`, `oaiusercontent.com`
- Claude: `claude.ai`, `claude.com`, `claudeusercontent.com`, `anthropic.com`

Ограничение: доменных записей не больше **8**, так что выбирайте важное.

В командной строке это выглядит так (для проверки по SSH: `ndmc -c "show running-config" | grep tls`):
```
dns-proxy tls upstream <IP_DNS_СЕРВИСА> sni <dns.сервис.ru> domain chatgpt.com
```

## 2.3. Проверка

На ПК (PowerShell), DNS должен быть роутер:
```
Resolve-DnsName chatgpt.com -Server 192.168.1.1
```
Адрес должен отличаться от того, что отдаёт обычный DNS (`-Server 8.8.8.8`). Потом откройте сайт.

## Проверка на утечку

**Ловушка, на которую уходит полдня.** Кроме обычной записи (A) у сайтов бывает запись **HTTPS** (тип 65) с
подсказкой адреса (`ipv4hint`). Некоторые DNS-прокси подменяют A-запись, а в HTTPS-записи оставляют **настоящий
адрес**. iPhone и Safari берут адрес оттуда, идут напрямую, и сервис видит ваш домашний IP («недоступно в вашей
стране»), хотя на ПК всё работает.

Проверка (`nslookup` есть в Windows):
```
nslookup -q=TYPE65 chatgpt.com 192.168.1.1
```
Если в ответе есть `ipv4hint` с адресом, который **не** совпадает с адресом прокси, этот DNS-сервис протекает.
Возьмите другой.

## Приложение работает через раз

Сайт в браузере открывается, а приложение на телефоне работает через раз. Две частые причины:

1. **У прокси несколько узлов, и часть из них мёртвые.** DNS отдаёт то один, то другой (TTL короткий). Проверьте
   узлы по очереди с ПК:
   ```
   curl.exe -s -o NUL -w "%{http_code} %{time_total}\n" --resolve "claude.ai:443:<IP_УЗЛА>" https://claude.ai/
   ```
   Рабочий узел быстро отвечает кодом (200/302/403), мёртвый даёт `000`. Закрепите хороший в командной строке роутера:
   ```
   ip host claude.ai <IP_ХОРОШЕГО_УЗЛА>
   system configuration save
   ```
   То же для доменов, которыми ходит приложение (для Claude это `api.anthropic.com`, `a-api.anthropic.com`,
   `claudeusercontent.com`). Если узел потом умрёт, переизмерьте и перезакрепите.

2. **Приложение ходит по QUIC (HTTP/3 поверх UDP 443)**, а прокси или путь до него с UDP работает плохо. Запретите
   UDP 443 к закреплённому адресу, и приложение откатится на обычный HTTPS (TCP):
   **Сетевые правила → Межсетевой экран → Домашняя сеть → Добавить правило**: Запретить, протокол UDP, назначение
   `<IP_ХОРОШЕГО_УЗЛА>`, порт 443.
